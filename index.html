대본: XFS 위의 pNFS block layout

번호는 발표 화면의 slide 번호, 굵은 [k]는 그 slide에서 k번째 클릭 뒤에 할 말이다. 수치는 화면에 있는 것만 말한다.

조작: → 또는 space 다음 클릭, ← 이전 클릭, PageDown/PageUp(clicker)도 같다. mouse wheel은 아래로 다음 클릭, 위로 이전 클릭(한 번 굴림에 한 단계). 마우스는 펜이다(처음부터 켜져 있음). p 펜 켜고 끄기, c 그린 것 지우기, Ctrl+Z 되돌리기, 1~7 색, Esc 펜 끄기. 펜을 끈 뒤 o 전체 목록, g 번호로 가기.

1. s01 XFS 위의 pNFS block layout (0.5분, 끝나면 누적 0.5분)

[0] 이 구성은 어떤 workload에 맞을까요? pNFS는 NFSv4.1의 확장입니다. client가 data를 server를 거치지 않고 device에 직접 씁니다. MDS는 metadata를 맡는 server입니다. 근거는 둘, kernel code와 VM 실험입니다.

2. s02 여러 AI node, file system 하나 (1분, 끝나면 누적 1.5분)

[0] 이런 구성을 생각해 봅니다. 학습 node 여러 대가 file system 하나를 같이 씁니다. 모든 node가 같은 file을 봅니다.

[1] 이 storage에 오는 일은 셋입니다. 첫째, 큰 dataset을 읽습니다. 둘째, checkpoint입니다. 학습 도중의 model 상태를 큰 file로 쓰고 끝에 fsync합니다. 셋째, 추론의 KV cache를 file로 자주 쓰고 지웁니다.

[2] 그래서 오늘의 질문은 이것입니다. 이 storage로 pNFS block layout은 맞을까요? 답은 workload에 따라 갈립니다.

3. s03 layout과 data 경로 (2.5분, 끝나면 누적 4분)

[0] 화면에 넷이 있습니다. 왼쪽에 client 둘, 가운데 MDS, 오른쪽에 모두가 같이 보는 device입니다. MDS는 metadata server의 줄임말입니다. file의 이름과 크기, block 할당과 위치를 맡습니다. 여기서는 Linux의 nfsd와 그 아래의 XFS입니다. pNFS는 NFSv4.1에 들어 있는 확장입니다. client가 data를 MDS를 거치지 않고 device에 직접 읽고 쓰게 합니다.

[1] 먼저 layout이 없는 보통의 NFS입니다. 주황색 data가 전부 MDS를 지나죠. MDS가 client 대신 device에 씁니다.

[2] layout을 받으면 달라집니다. client는 MDS에 어디에 쓸지만 묻습니다. data는 device로 바로 갑니다. 그럼 MDS에는 무엇이 남을까요? block 할당, metadata 변경, 그리고 그것을 log에 남기는 일입니다. 이 남는 일이 오늘 볼 비용입니다.

[3] 연결은 셋입니다. client와 MDS 사이의 control link, client와 device 사이의 data link, MDS와 device 사이의 link입니다. 실험은 이 넷을 한 host 안의 VM으로 만들었습니다. 세 연결이 모두 가상 network라 속도의 비가 실제 장비와 다릅니다. 그래서 오늘은 속도 이야기가 아닙니다. 횟수와 순서, 대조군과의 비를 봅니다.

4. s04 먼저 답 (1.5분, 끝나면 누적 5.5분)

[0] 답을 먼저 드리겠습니다. 큰 file을 client마다 따로 읽고 쓰면 맞습니다. MDS의 일이 거의 없기 때문입니다. 약한 곳은 세 칸입니다.

[1] 첫째, 비용입니다. layout을 쓰면 data는 MDS를 지나지 않습니다. 그런데 MDS의 일은 bytes가 아니라 횟수를 따릅니다. file을 여는 횟수, fsync 횟수, file이 조각난 정도입니다. 큰 file을 client 하나가 다루면 그 일이 거의 없고, 작은 file이 많으면 커집니다.

[2] 둘째, 공유입니다. 두 client가 한 file에 쉬지 않고 계속 I/O를 내면, 읽기끼리라도 한쪽이 거의 쓰지 못했습니다.

[3] 셋째, 장애입니다. fsync가 성공했는데 data가 0으로 읽힌 경우가 있었습니다. 이 세 칸을 보이려면 각 component가 어떻게 움직이는지 알아야 합니다. 그래서 pNFS와 XFS의 기본 작동부터 보겠습니다.

5. n1 pNFS의 component (0.25분, 끝나면 누적 5.75분)

[0] 먼저 pNFS입니다. client와 MDS의 nfsd 사이에 무엇이 오갈까요? 그것부터 보겠습니다.

6. s05 layout이란 (1.5분, 끝나면 누적 7.25분)

[0] 오늘 가장 많이 나올 낱말이 layout입니다. 이것부터 정의하겠습니다.

[1] 위가 file, 아래가 device입니다. 파란 점선이 file의 이 범위가 device의 어느 block에 있는지를 잇습니다. 이 대응의 목록이 layout의 몸통입니다. 한 덩어리를 extent라고 부르고, MDS에서는 XFS가 이 목록을 만들어 줍니다.

[2] 여기에 권한이 붙습니다. 읽기만 하는 READ, 읽고 쓰는 RW입니다. RW layout을 받은 client는 그 block에 직접 씁니다.

[3] 마지막으로 file을 닫으면 돌려준다는 표시가 붙습니다. Linux server는 이 표시를 늘 켜서 보냅니다. code로 확인했습니다. layout은 두 번 더 나옵니다. 4막에서 write 하나를 따라갈 때, 6막에서 두 client가 다툴 때입니다.

7. s06 layout type 셋 (1.5분, 끝나면 누적 8.75분)

[0] Linux nfsd가 내주는 layout type은 셋입니다.

[1] block과 SCSI는 client가 shared device에 직접 bio를 냅니다. flexfiles는 다릅니다. device가 아니라 같은 server에 NFSv3 RPC로 data를 보냅니다.

[2] export op는 nfsd가 filesystem에 부르는 함수입니다. block은 셋, SCSI는 둘을 부릅니다. 기준 tree에서 이 함수를 가진 filesystem은 XFS 하나뿐입니다. 그래서 오늘은 XFS 위의 block과 SCSI만 봅니다.

[3] 함정이 하나 있습니다. layout이 쓰이려면 아래 네 조건이 다 맞아야 합니다. 하나라도 어긋나면 error 없이 I/O가 MDS로 갑니다. mount 정보에 pnfs가 보여도 driver 설정일 뿐입니다. 9막에서 RPC 수로 확인하라고 다시 말씀드리겠습니다. 조건의 대부분은 code로 확인했습니다.

8. s07 operation 넷과 recall (2분, 끝나면 누적 10.75분)

[0] layout 하나가 오가는 순서를 따라가 보겠습니다.

[1] 처음 쓰려는 순간, client가 LAYOUTGET으로 그 범위의 block 위치를 받습니다. OPEN에 싣지 않고 첫 I/O 때 보냅니다. MDS 안에서는 XFS의 map_blocks가 답합니다.

[2] layout은 device를 ID로 가리킵니다. 처음 보는 ID면 GETDEVICEINFO로 그 device가 무엇인지 묻습니다. block layout이면 XFS의 get_uuid가 답합니다.

[3] 이제 client가 device에 직접 읽고 씁니다. 이 동안 MDS는 아무것도 모릅니다.

[4] 다 쓰면 LAYOUTCOMMIT으로 쓴 범위와 새 file size를 알립니다. 이때 XFS의 commit_blocks가 그 block을 읽을 수 있는 상태로 바꿉니다. 이 말은 3막에서 다시 풀겠습니다.

[5] 다 쓴 layout은 LAYOUTRETURN으로 돌려줍니다. 보통 CLOSE에 실어 보내죠. 그런데 MDS가 먼저 돌려 달라고 할 때가 있습니다. 그 callback이 CB_LAYOUTRECALL, 줄여서 recall입니다. client는 받으면 LAYOUTRETURN으로 돌려줍니다.

9. s08 layout의 상태: stateid, file lease, client lease (1.5분, 끝나면 누적 12.25분)

[0] MDS는 layout에 대해 무엇을 기억할까요? 셋입니다.

[1] 첫째, stateid입니다. client와 file의 짝마다 하나입니다. 기억하는 것은 어느 범위를 어떤 권한으로 줬는지뿐입니다. 내준 block 목록은 기억하지 않습니다.

[2] 둘째, file lease입니다. layout을 처음 내줄 때 MDS가 그 file에 걸어 둡니다. 누가 그 file을 바꾸려 하면 MDS가 먼저 압니다. 그 연산은 layout이 돌아올 때까지 최대 45초를 기다립니다. 충돌은 file 단위로만 따집니다. 범위와 iomode는 보지 않습니다. code로 확인했습니다.

[3] 셋째, client lease입니다. client는 90초 안에 갱신해야 하고, 못 하면 MDS가 그 client의 상태를 버릴 수 있습니다. 이름은 비슷하지만 둘은 다른 것입니다. 7막에서 두 timer가 섞인 숫자가 나옵니다.

10. s09 recall의 계기 (1.5분, 끝나면 누적 13.75분)

[0] 그럼 recall은 언제 일어날까요?

[1] 계기는 둘입니다. 하나는 MDS에서 그 file을 바꾸는 연산입니다. write, fallocate, size를 바꾸는 setattr 같은 것이죠. 다른 하나는 다른 client의 LAYOUTGET입니다. 아래 회색 글, 읽기와 지우기와 이름 바꾸기는 계기가 아닙니다. 지우기가 빠지는 것은 block 해제가 마지막 참조가 사라질 때까지 미뤄지기 때문입니다.

[2] 계기에 따라 기다리는 방식이 다릅니다. MDS에서 file을 바꾸는 연산이면 file lease를 통해 recall을 보냅니다. 그 연산은 layout이 돌아오거나 45초가 지날 때까지 기다립니다. 다른 client의 LAYOUTGET이면 file lease를 거치지 않습니다. 요청한 쪽은 거부를 받고 다시 요청합니다. 이쪽에는 45초 timer가 없습니다. 그동안 그 file의 LAYOUTGET은 전부 거부됩니다.

11. s10 block과 SCSI: 찾는 법, 막는 법 (1분, 끝나면 누적 14.75분)

[0] 두 type은 어디서 갈릴까요? 두 군데입니다.

[1] 첫째, device를 찾는 법입니다. block은 device 안에 적힌 표식을 client의 daemon이 찾아 맞춥니다. SCSI는 device ID와 등록한 key로 찾습니다.

[2] 둘째, 말을 듣지 않는 client를 막는 법입니다. SCSI는 device의 reservation에서 그 client의 key를 지워 쓰기를 막으려 합니다. 이것을 fence라고 부릅니다. block에는 막을 수단이 없습니다. 7막에서 둘 다 실제로 해 봅니다.

12. s11 client I/O의 세 갈래 (1분, 끝나면 누적 15.75분)

[0] client의 I/O 하나는 세 길로 갈립니다.

[1] 위쪽 길입니다. layout이 있으면 extent를 찾아 device로 bio를 냅니다. 끝나면 끝난 것으로 표시하고, LAYOUTCOMMIT은 나중에 보냅니다.

[2] 가운데 길입니다. 충돌이나 server 재기동 직후처럼 지금은 못 준다는 error를 받으면, 기다렸다 다시 묻기만 합니다. 간격은 0.1초에서 두 배씩 15초까지 늘고, MDS로는 가지 않습니다. 6막에서 이것이 문제가 됩니다.

[3] 아래쪽 길입니다. layout을 못 받거나, device를 못 열거나, bio가 error면 MDS로 돌아갑니다.

14. s12 AG와 free space (1.5분, 끝나면 누적 17.5분)

[0] XFS는 device를 어떻게 나눠 쓸까요? 뒤에서 file이 쪼개지는 이야기를 하려면 이 그림이 필요합니다.

[1] device는 같은 크기의 AG로 나뉩니다. AG마다 빈자리를 두 가지로 정리해 둡니다. block 번호순과 길이순입니다. 가장 긴 빈자리의 길이도 따로 적어 둡니다. 기억하실 것은 하나입니다. 할당 한 번은 한 AG 안에서 끝나고, 여러 AG에 걸치지 않습니다.

[2] file의 inode는 parent directory가 있는 AG에 자리를 잡습니다. 첫 data는 그 inode 근처부터 찾습니다.

[3] 그러면 여러 client가 한 directory에 file을 만들면 어떻게 될까요? MDS의 할당이 그 directory의 AG에 먼저 모입니다. 5막에서 file이 쪼개지는 이야기로 이어집니다. 여기까지는 code로 확인했습니다.

15. s13 extent와 unwritten (1.5분, 끝나면 누적 19분)

[0] 이번에는 file 하나를 들여다봅니다. 위가 file의 offset, 아래가 device의 block입니다.

[1] file의 data가 어디 있는지는 extent라는 record의 목록에 적힙니다. record 하나는 네 값입니다. file의 어디가, device의 어디에, 얼마나 길게, 어떤 상태로 있는지입니다.

[2] record가 몇 개 안 되면 inode 안에 둡니다. 많아지면 inode 밖의 btree로 옮깁니다. 4막의 LAYOUTGET은 XFS에서 이 record를 하나씩 받아 갑니다.

[3] 여기서 중요한 것은 상태입니다. 할당했지만 아직 쓰지 않은 block은 unwritten입니다. 읽으면 0이 나옵니다. 그 자리의 옛 data를 보이지 않게 하려는 것이죠. data를 쓴 뒤 written으로 바꾸는 transaction이 따로 듭니다. 7막의 유실 둘은 이 unwritten에서 시작합니다.

16. s14 할당의 세 경로 (2분, 끝나면 누적 21분)

[0] 같은 allocator를 세 경로가 부릅니다. 차이는 둘, 언제 잡느냐와 얼마나 잡느냐입니다.

[1] 첫째, local buffered write입니다. write 때는 block을 정하지 않고 예약만 합니다. 이것을 delalloc이라고 합니다. writeback 때 이어진 범위 전체를 한꺼번에, file 끝 뒤까지 넉넉하게 잡습니다. I/O가 끝나면 written으로 바꿉니다.

[2] 둘째, local direct I/O입니다. write system call 안에서 그 write의 길이만큼 잡고, I/O가 끝나면 written으로 바꿉니다.

[3] 셋째, pNFS입니다. LAYOUTGET이 온 그 자리에서 요청한 범위만큼 잡습니다. 범위를 자르는 code는 없습니다. written이 되는 것은 client가 다 쓰고 LAYOUTCOMMIT을 보낼 때입니다. 아래 줄처럼 세 경로 모두 새 extent는 unwritten으로 시작합니다. 이 차이 때문에 5막에서 pNFS file이 더 잘게 쪼개집니다.

17. s15 할당 한 번의 순서 (1.5분, 끝나면 누적 22.5분)

[0] 할당 한 번의 안쪽입니다. AG 0에 이 file의 extent가 하나 있습니다. 다음 write는 어디에 놓일까요?

[1] file 끝에 덧붙이는 write면 앞 extent 바로 뒤 block을 목표로 잡습니다. 이어 붙이면 extent가 늘지 않기 때문입니다.

[2] 그런데 목표 자리에 요청한 길이가 다 들어가지 않으면요? 그 길이가 통째로 들어가는 빈자리가 어느 AG에든 있으면 그 AG로 옮겨서라도 한 번에 잡습니다. 쪼개지 않는 쪽을 고르는 것이죠.

[3] 어느 AG에도 그런 자리가 없으면 짧게 받고 나머지를 다시 요청합니다. pNFS에서는 nfsd가 다음 offset으로 XFS를 다시 부릅니다. 그때마다 transaction 둘과 log force 하나가 더 듭니다. 여기는 code로 확인했고, 5막의 조각난 file 실험이 그 결과입니다.

18. s16 transaction과 log force (2분, 끝나면 누적 24.5분)

[0] XFS가 바뀐 metadata를 device에 남기는 길입니다. 네 칸을 왼쪽에서 오른쪽으로 따라갑니다.

[1] transaction을 commit하면 바뀐 것을 memory의 목록에 넣고 바로 돌아옵니다. I/O가 없습니다. 이 목록을 CIL이라고 부릅니다.

[2] 누군가 log force를 부르면 그 목록을 log buffer로 옮겨 device에 씁니다. 이때 device의 write cache를 비우는 flush와 FUA를 붙입니다. 그래서 log force 한 번은 device의 cache flush까지 기다립니다.

[3] log force를 부른 쪽은 그 write가 끝날 때까지 잡니다. pNFS에서 MDS가 device를 기다리는 자리가 바로 여기입니다. LAYOUTGET과 LAYOUTCOMMIT 안에서 이 대기가 일어납니다.

[4] 같은 때 다른 쪽도 log force를 부르면 어떻게 될까요? 같은 log buffer에 함께 실리고, flush 한 번이 둘을 깨웁니다. 그래서 부른 횟수와 flush 횟수가 다릅니다. 5막에서 log force를 셀 때 이 점이 다시 나옵니다. 여기까지는 code로 확인한 순서입니다.

19. s17 fsync와 LAYOUTCOMMIT (1.5분, 끝나면 누적 26분)

[0] fsync는 무엇을 할까요? 왼쪽 local, 오른쪽 pNFS로 나눠 봅니다.

[1] local fsync는 세 단계입니다. 그 범위의 dirty page를 먼저 씁니다. unwritten을 written으로 바꾸는 변환을 기다립니다. 그리고 inode가 기억한 변경까지 log force를 합니다.

[2] pNFS는 다릅니다. layout으로 쓴 범위는 client의 fsync가 MDS의 fsync를 부르지 않습니다. 대신 LAYOUTCOMMIT 끝의 sync transaction이 log force와 device cache flush를 맡습니다. MDS와 client가 같은 device의 같은 write cache를 본다는 전제입니다. 정리하면, LAYOUTCOMMIT이 끝나야 client가 쓴 data가 다른 쪽에서 보이고 crash 뒤에도 남습니다. 4막과 7막에서 이 점이 계속 나옵니다.

38. s32 recall 도중의 유실 (3.5분, 끝나면 누적 56.5분)

[0] fsync가 성공했는데 data가 0으로 읽힌다면, 어디서 사라진 걸까요? 4막에서 본 빠지는 길의 첫째입니다. client는 새 file에 512 MiB를 1 MiB씩 순서대로 쓰고, 끝에 한 번 fsync합니다. 그동안 MDS에서는 1초마다 같은 file에 truncate -s 4G를 겁니다. size만 4 GiB로 늘리는 것이라, 이미 쓴 범위는 자르지 않습니다.

[1] client가 LAYOUTGET으로 layout을 받습니다. XFS는 그 범위를 unwritten으로 잡습니다.

[2] client는 device에 직접 씁니다. LAYOUTCOMMIT은 아직입니다. 끝의 fsync 때 보낼 생각이죠.

[3] 그 사이 MDS의 truncate가 file lease를 깹니다. nfsd는 client에 recall을 보냅니다.

[4] 여기가 핵심입니다. client가 돌려준 LAYOUTRETURN이 LAYOUTCOMMIT보다 먼저 MDS에 닿았습니다. 그러면 MDS는 늦게 온 LAYOUTCOMMIT을 NFS4ERR_BADLAYOUT으로 거부합니다. 그런데 client는 이 거부를 성공으로 처리하고 넘어갑니다. 빨갛게 표시한 자리입니다. 근거는 셋으로 나뉩니다. 첫째, LAYOUTRETURN이 먼저 닿는 순서는 계속 쓰는 조건에서 trace로 봤고, 유실이 난 실행에서는 거부 네 번을 봤습니다. 둘째, 거부가 닫힌 stateid 때문이라는 것과 거부를 성공으로 바꾸는 것은 code로 확인했습니다. 셋째, 왜 그 순서가 되는지는 예측입니다.

[5] 그래서 application의 fsync는 성공합니다. 오른쪽 막대를 보시죠. recall이 난 네 번의 실행에서 512 block 가운데 6, 148, 4, 3개가 0으로 읽혔습니다. recall이 없던 세 번은 0개였고, client를 다시 mount해 읽어도 0이었습니다. commit되지 못한 범위가 unwritten으로 남았기 때문입니다.

39. s33 commit 전 MDS 재기동 (2.5분, 끝나면 누적 59분)

[0] 둘째 길입니다. 이번에는 recall이 아니라 MDS가 멈추면 어떻게 될까요?

[1] client가 layout을 받아 새 범위에 64 MiB를 썼습니다. 아직 LAYOUTCOMMIT 전입니다. 그래서 MDS에서 이 file은 size 0이고, 범위는 unwritten입니다.

[2] 이때 MDS를 강제로 끄고 다시 띄웠습니다. 그 뒤 client가 fsync를 합니다. LAYOUTCOMMIT은 error를 받는데, client는 그 error를 성공으로 처리하고 다시 보내지 않습니다. 그래서 fsync는 성공합니다. 하지만 오른쪽 칸처럼 MDS에서 file은 여전히 size 0, 범위는 unwritten이었습니다. error를 성공으로 바꾸는 것은 code로 확인했습니다. client 한 대로 한 번 실행했고, device의 write cache는 남아 있는 조건입니다.

[3] 재기동 뒤에는 grace가 있습니다. 재기동한 server가 예전 상태를 되찾는 동안 새 요청을 거부하는 기간입니다. 이 동안 LAYOUTGET은 거부되고, client는 재시도만 하며 MDS로 돌아가지 않습니다. 화면의 열 번, 57.4초는 NFSv3을 같이 내준 구성에서 lockd의 grace 50초에 묶인 값입니다. data를 본 실행과는 다른 실행입니다. 예상한 90초와 달랐던 것은 nfsd의 grace가 그 전에 끝났기 때문입니다.

[3] 그런데 주황 화살표를 보시죠. 끊긴 C1은 들고 있던 layout으로 device에 계속 썼습니다. 2막에서 본 대로 block layout에는 그 client를 막을 수단이 없습니다. MDS는 진행했다고 여기는데, device에는 다른 쪽의 쓰기가 계속 들어옵니다.

1. 실제 장비에서는?

device가 한도가 되는 지점은 판정하지 못했습니다. job 수 실험에서 T의 backing을 실제 NVMe partition으로 바꿔도 operation 수는 raw file의 0.91~1.20배였습니다. 이 환경의 한도는 device가 아니라 가상 network였습니다. 결론은 횟수와 순서로 냈고, 시간의 비와 교차하는 크기는 이 환경의 값입니다.

보일 slide: slide 50 (0), slide 59

2. flexfiles는?

이 조사의 범위 밖입니다. Linux nfsd의 layout type은 셋입니다. flexfiles는 XFS의 export op를 부르지 않습니다. Linux nfsd에서는 data가 같은 server에 NFSv3 RPC로 갑니다.

보일 slide: slide 7 (2)

3. 왜 SCSI fence가 막지 못했나?

Linux nvmet이 다른 등록을 지우지 않았기 때문입니다. nfsd의 preempt는 성공을 돌려줬습니다. NVMe Base Specification 2.1은 지우라고 하므로 nvmet 쪽의 차이입니다. 고치는 patch가 nvme-7.4에 들어갔습니다. 다른 device(sd, 실제 NVMe device)에서는 확인하지 못했습니다.

보일 slide: slide 42 (2), slide 45 (1)

4. 기준 이후 upstream에서는?

client 쪽은 확인하지 못했습니다. pnfs_layout_need_return 비교를 고친 203582017774가 recall 도중 유실에 가장 가깝지만 그 위에서 돌리지 않았습니다. nfsd 쪽은 우리가 낸 recall 수정이 nfsd-testing에 들어갔습니다.

보일 slide: slide 46 (2), slide 50 (0)

5. layout 없는 NFS와 어떻게 비교했나, 대조군은 무엇인가?

대조군은 둘입니다. 같은 export에서 pnfs만 뺀 layout 없는 NFS와 local XFS입니다. 같은 workload의 횟수와 시간의 비를 냈습니다. 예를 들어 새 file 100개 write와 fsync에서 log force는 layout 400, layout 없는 NFS 300, local XFS 101이었습니다.

보일 slide: slide 26 (1), slide 58

6. 한 번 실행한 결과를 믿을 수 있나?

일어났다는 관측으로만 씁니다. 빈도는 말하지 않습니다. 한 번 실행한 것은 file 공유, client 차단, 재기동 실험과 조각난 file 실험의 write arm입니다. 화면에는 “1회”로 표시했습니다.

보일 slide: slide 50 (0), slide 62

7. 문헌의 KV cache 크기에서는?

그 크기는 실험하지 않았습니다. 실험한 KV cache object는 256 KiB~16 MiB였습니다. file마다 log force가 4~4.5회(KV cache 반복 실험에서 4.5) 드는 작은 새 file 쪽입니다. 문헌의 수십 MiB~수 GiB는 큰 file 쪽에 가깝다고 예측합니다.

보일 slide: slide 48 (2)

8. FDP는?

이 조사의 범위 밖입니다. FDP와 device 쪽 write amplification은 다루지 않았습니다.

보일 slide: 없음

9. XFS 말고 다른 filesystem은?

기준 tree에서는 XFS 하나뿐입니다. block과 SCSI layout이 부르는 export op map_blocks를 XFS만 구현합니다. 다른 filesystem에는 nfsd가 이 두 layout을 내주지 않습니다.

보일 slide: slide 7 (2)

10. VM 환경의 한계는?

속도의 비가 실제 장비와 다릅니다. host 1대 위 VM 4대, 세 연결 모두 가상 network입니다. device는 Linux nvmet입니다. 그래서 절대 throughput과 latency는 결론에 쓰지 않았습니다.

보일 slide: slide 3 (3), slide 58

11. 운영할 때 무엇을 피해야 하나?

본문의 다섯입니다. layout이 쓰이는지 확인합니다. 한 file을 여러 client가 같이 쓰지 않습니다. layout이 나간 file은 MDS에서 건드리지 않습니다. SCSI layout은 device의 fence부터 확인합니다. mount 뒤 file 하나를 먼저 읽어 둡니다. 나머지 다섯은 부록에 있습니다.

보일 slide: slide 49 (5), slide 64

12. slide 38의 유실과 nfsd patch가 고친 것은 같은 원인인가?

기준 kernel에서 같은 원인인지 대조하지 않았습니다. patch가 고친 것은 nfsd가 recall을 실패로 처리해 layout을 버리던 경로입니다. client가 NFS4ERR_BADLAYOUT을 성공으로 바꾸는 동작은 남았습니다. nfsd-testing에서는 같은 조작의 유실이 patch 앞 판에서 0이 됐습니다.

보일 slide: slide 46 (2)

13. LAYOUTRETURN이 먼저 닿는 원인이 예측이라면 유실의 원인은 확정인가?

예측은 그 순서의 까닭 하나뿐입니다. 관측한 것은 셋입니다. 넷째 실행에서 LAYOUTCOMMIT 14회 가운데 4회가 NFS4ERR_BADLAYOUT을 받은 것, fsync 성공, 0으로 읽힌 block입니다. LAYOUTRETURN이 LAYOUTCOMMIT보다 먼저 닿는 순서는 같은 실험의 계속 쓰는 조건에서 trace로 관측했습니다. 거부가 닫힌 stateid 때문인 것과 client가 그 거부를 성공으로 바꾸는 것은 code로 확인했습니다.

보일 slide: slide 38 (4)

14. log force 400회는 device flush 400회인가, 묶이지 않나?

하나씩 부르면 같고, 같은 때 부르면 묶입니다. RPC 회계 실험에서는 M의 log write가 400회로 log force 400회와 같았습니다. 학습 process 넷이 동시에 쓰는 checkpoint 실험에서는 log force 520회에 iclog write가 396회였습니다.

보일 slide: slide 29 (3), slide 18 (4)

15. layout이 나간 file을 MDS 쪽이 바꿀 일이 실제로 있나, 다른 client의 LAYOUTGET이 건 recall에서도 data가 사라지나?

유실은 MDS의 size 변경으로만 대조했습니다. 계기는 MDS에서의 write, fallocate, size 변경, reflink remap, scrub repair와 다른 client의 LAYOUTGET입니다. 다른 계기에서는 data를 대조하지 않았습니다. AI workload에서 이런 연산이 얼마나 나는지는 보지 않았습니다.

보일 slide: slide 10 (1), slide 50 (0)

16. 시간을 결론에 쓰지 않는다면서 “느렸다”, “멈췄다”는 어떻게 아나?

같은 조건의 대조군과 code의 timer 상수에 대한 비만 썼습니다. 지연 주입 실험의 64 KiB file 1,000개에서 layout / layout 없음 0.73, timer는 46.1 / 45 = 1.03입니다. 초는 timer와 맞댈 때만 썼습니다.

DLIO로는 돌리지 않았습니다. 같은 I/O pattern을 script로 냈고, DLIO가 이 환경에서 동작하는 것만 확인했습니다.
